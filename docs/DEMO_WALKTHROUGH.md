# MYA 完整演示流程与实测记录

更新：2026-09-15。标题：**MYA — AI Authenticator for Any Agent**。副标题：远程可信审批、用户与 Agent 的密码学关系绑定。

本流程用于讲解和复现。表中“真人”来自本次用户手机操作；“自动测试”使用隔离身份；“待验收”不得展示为成功。所有投递仅进入演示收件箱。

## 讲解开场（1 分钟）

“工作交给 Agent，决定留在您手里。MYA 先让用户与具体 Agent 建立密钥关系，再通过手机独立审阅行动并签署授权。钱包把授权出示给受信资源，资源核验后执行，最后给出签名回执。审批分支可提出修改，未来接入独立调查 Agent；当前分析建议和指纹按钮为模拟，签名和执行端校验是真实的。”

远程审批、密码学确认已有 CIBA、Guardian、OneSpan 等先例，不能称 MYA 独有。MYA 的产品假设是将持续 Agent 关系、双向审批分支、行动凭证和用户侧决策辅助组合起来；兼容任何 Agent、标准 VC 互通、组织审批和反诈效果尚需独立验证。

## 0. 准备与部署（预先完成）

- PC：Node24、`npm ci`、`npm run build`、`npm test`、`npm link`、`npm run install:skill`。
- Oracle：Node 服务、持久化密钥/SQLite、systemd、HTTPS 反代；参考 [DEPLOYMENT.md](DEPLOYMENT.md)。当前服务代码为 `0240f65`，Hook 运行在 PC，本次不需要重新部署服务。
- 手机：打开 `https://mya-esand.duckdns.org/mobile/`，测试时页面保持前台；无需 App。
- 初始化：`mya init --server https://mya-esand.duckdns.org --trust-witness TRUSTED_FINGERPRINT`。指纹从受信服务器控制台核对，不从未知响应自动接受。
- 演示前 `mya doctor`、`mya bindings`。客户端有 active 绑定，不足以证明当前手机浏览器持有该绑定的私钥。

## 1. Show 绑定（2 分钟）

1. PC 执行 `mya pair`，保持运行；同时展示二维码、8 位配对码和手机邀请链接。
2. 手机扫码失败时，打开正确 HTTPS 页面，点“输入配对码”。配对码用来加入邀请，后面两端展示的短码用来核对同一关系。
3. 用户核对两端短码一致，在手机和 PC 分别确认。手机生成本地密钥、签署关系；Agent 证明持有其私钥；见证签署双方一致的绑定材料。
4. 展示手机“我的 Agent”和 PC 绑定列表，明确绑定不等于同意以后所有行动。

**本次真人排障：** 手机显示“连接第一个 Agent”；确认 PC 配置、服务公钥和手机静态文件同属 Oracle 部署后，重新配对完成。第一次邀请超时，第二次提供二维码+配对码成功。PC 确认页是 `127.0.0.1`，远程浏览器无法直接访问 PC 回环地址；用户明确授权 Agent 代点 PC 端确认，手机由用户确认。这是本次远程操作的例外，不能宣传为用户亲自点击了两端。旧关系保留，未删除密钥来强行修复。

## 2. 成本报告 → 要求修改（2 分钟）

```sh
mya request --file fixtures/request-cost.json
mya status --request REQUEST_ID --wait 20
```

手机展示实际接收方、目的、内容和模拟建议。用户要求移除内部成本/个人信息，只保留进度字段。Agent 收到 `changes_requested` 后准备新文件，新增 `supersedes_request_id` 指向原请求。不要修改已冻结请求的内容来复用授权。

首次真人记录：原请求 `5fdd1ce3-3d41-4de0-a8c4-5d71a245eded`，修订 `bd4ba443-b85b-44e3-bf83-19e1057b1a7e`。修订获批后有签名执行回执。

## 3. 安全版本 → 持续等待手机批准（1 分钟）

从 `fixtures/request-safe.json` 创建本轮输入；多绑定时显式填写 `binding_id`，文件路径相对于输入文件。循环 `mya status --request ID --wait 20` 至决定、过期、取消或持续错误，期间简要汇报等待状态。不要让用户回到主会话再说“批准了”才能继续。

本次新手机真人请求 `5a0ad59f-2c45-4130-b343-c65bf977e1b8`：Agent 轮询拿到手机批准后自动执行；用户随后在聊天里说“批准了”，这不是执行依据。

## 4. 钱包挑战出示与执行（2 分钟）

```sh
mya execute --request REQUEST_ID --presentation
mya receipt --request REQUEST_ID
mya inspect --request REQUEST_ID
```

分步展示时用 `mya challenge --request ID --out challenge.json`，再 `mya present --request ID --challenge challenge.json`；出示本身不执行。

讲解流水：资源冻结请求并签署挑战 → 钱包核验固定服务、公钥、验证端点、交易号、nonce、行动摘要 → 附上既有关系/授权凭证并签署持钥证明 → 验证服务记录逐项结果 → 资源再次校验、单次消费并执行 → 签署回执。

凭证可以被对方读取，并不代表可被篡改而继续通过验签；仍包含隐私，只应发给被授权的受信验证方。当前采用自定义 JWS 凭证，不是完整 DID/VC 或 OpenID4VP 产品。Agent 本机钱包尚未做独立 OS/硬件隔离。

## 6. 单独启用自动规则与例外（2 分钟，可选）

手机从 Review 创建规则草案，由用户单独确认启用；同收件人、同项目、允许字段、限额/次数/时间内的请求可自动批准。换收件人、出现未知字段、超限、规则暂停或关系撤销时不能沿用旧权限。

当前这些能力通过隔离浏览器/协议自动测试；没有把真人用户这次单次批准视为同意启用规则。现场要展示真人启用时，必须让用户在手机单独操作。

## 收尾（1 分钟）

展示“谁发起、用户要求怎样修改、批准哪个版本、出示给谁、最终执行了什么”的关联证据。强调三层分工：Skill 负责协作，Hook 负责受支持入口的前置门禁，资源端负责执行授权。下一阶段以真实原生拦截、结构化工具、独立钱包/执行权限和独立调查证据作为验收目标。
